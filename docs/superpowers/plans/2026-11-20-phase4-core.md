# Phase 4 core — Schedule Engine, Grid, Gantt and Editor Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the app into a working scheduling tool: every schedule opens on `/w/:workspaceId/p/:projectId/schedule` from a versioned gzipped `ScheduleDocument` snapshot, a pure TypeScript CPM engine runs in its own Web Worker under explicit `p6` / `msp` / `default` profiles, and planners read and edit the schedule in a virtualized grid with a Canvas 2D Gantt, a docked inspector, search and an explicit-save Edit mode guarded by database version locks and Undo/Redo.

**Architecture:** One pgTAP-tested migration (`p4_core_schedule_data`) adds the `schedule-data` bucket, lock/revision columns and six RPCs; it lands with the adapter code that adapts to it. The repository contract then grows the document and lock methods on both adapters. A pure TypeScript engine in `src/engine` (ESLint-bounded, battery- and property-tested in Node, oracle-ratcheted against fixture dates) materializes `ImportModel`s and solves documents; it runs in a module Web Worker behind a typed `postMessage` client. Pure command functions give the editor validated mutations and Undo/Redo. The UI tasks build the schedule page, grid, Canvas Gantt behind a `Draw2D` seam, toolbar and inspector on hooks.

**Tech Stack:** the Phase 3 core stack plus `@tanstack/react-virtual` 3 (runtime) and `fast-check` 4 (dev only).

**Spec:** `docs/superpowers/specs/2026-11-20-phase4-core-design.md` ("the spec"). It builds on `docs/superpowers/specs/2026-11-05-phase3-core-design.md` ("P3 core"), which a task cites only where it needs a detail. Each task names its spec sections; values there are requirements even when the task doesn't repeat them.

## Review Focus

1. **A save while the lock is expiring, or after another user took an expired lock** (R2, R5). Expected: `save_schedule_data` refuses with the lock copy, the editor keeps the unsaved document in memory, shows "Your edit lock expired. Copy your changes or reload the schedule." and never overwrites the other user's snapshot. Pinned in Tasks 3, 5, 19 and 31.
2. **Deep and wide logic at the 50,000-activity limit** (one chain of 50,000 FS links; one activity with 5,000 successors). Expected: no stack overflow in topological sort, cycle search, passes or driving trace; solve inside the S6 budget. Pinned in Tasks 11, 14 and 16.
3. **"As imported" dates before the first calculation.** Expected: opening, materializing, rolling up, searching, selecting, toggling Edit and saving without Calculate never change any `sourceDates` value or the dates the grid and Gantt show. Pinned in Tasks 9, 15, 23 and 36.
4. **Leaving Edit mode with unsaved changes** (route change, schedule switcher, tab close, sign-out). Expected: the "Discard unsaved changes?" confirmation (or `beforeunload`), and the lock released best effort only after the user leaves. Pinned in Tasks 19, 22 and 31.
5. **Edge inputs:** zero-duration activities and milestones on non-working days, 24-hour elapsed lags, negative lags crossing the project start, empty WBS elements, calendars with exceptions only, activities without a calendar match. Expected: deterministic dates with the spec's warnings, never `NaN`, `Invalid Date` or a thrown error. Pinned in Tasks 7, 9, 12–15.
