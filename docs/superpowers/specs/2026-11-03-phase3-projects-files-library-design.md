## 1. Summary

Phase 3 replaces the Projects, Project files and Library placeholders with working screens, and gives schedules the file-level data the rest of the product builds on. Projects gain a status, a stage, a sector, a program, a time zone, a date and time format and map coordinates, show as tiles, a list or a map, and can be moved between programs or deleted. A project's files page keeps its schedules in folders, tags them (current, baseline, primary baseline, update n), saves frozen versions under them, makes independent copies, protects them against changes, archives them, keeps notes, shows who holds the edit lock and lets the holder or an owner release it; the database enforces every one of these rules, and every blocked action names its reason. **Import** reads Primavera P6 XER, Microsoft Project XML (MSPDI), Excel (.xlsx) and CSV in a Web Worker, several files and several P6 projects in one run, recognizes the format from the content, asks for a column mapping when the file is a spreadsheet, can replace an existing schedule's source (after a preview that counts the activities added, removed and changed) or reload it, and stores an **import report** (counts, what was used, kept or not read, automatic checks, every issue) next to the original file, downloadable as CSV, Excel or JSON. The **Library** lists every schedule the user can open, across workspaces, in workspace, project and folder order. Activities, WBS, relationships and calendars stay in Phase 4, which builds them from the stored original file and the stored mapping (D3).

The owner named a reference product on 2026-11-03: P3 matches its project, file, import and library functions and then improves on them (D32). This spec calls it "the reference product" and doesn't name it; every word of copy here is our own.

## 2. Goals, success criteria, non-goals

### 2.1 Goals

1. Every project carries the app-map §2.1 attributes and a scheduling time zone, and a workspace's projects can be found by search, filters and sort in three layouts.
2. A project's schedules behave like versioned files: exactly one current, any number of baselines with one primary, numbered updates, frozen saved versions, independent copies, protection, folders, notes, archive and a visible edit lock, all enforced by the database.
3. Imports from the three exchange formats are read faithfully enough to count, check and report every calendar, WBS element, activity and link; nothing is dropped without an entry in the report (the count rules of §5.9), and every source element is reported as used, kept or not read (§5.9).
4. Every function of the reference product in these areas has a counterpart here or a recorded reason why not (§12 D32–D52); improvements beyond it are the small ones inside the roadmap's P3 row (D52) and the three the owner approved on 2026-11-03: a change preview before a replace, the import report as an Excel download and a per-project date and time format (D64–D66). The other larger improvements are deferred with a seam (§2.3, D67).
5. Phase 4 adds its schedule model next to P3's tables and reads P3's stored original files and mappings, which nothing changes after the import; P4 adds the grants or functions it needs to refresh the report and the activity count (§5.8).

## 3. Architecture

```
Browser
  pages: ProjectsPage · ProjectFilesPage · LibraryPage           (replace the placeholders)
    → features: projects/ · files/ · library/ · import/ (UI)  →  hooks (src/hooks)
        ├─ DataRepository ─ MockRepository | SupabaseRepository   (only src/data/index.ts imports them)
        └─ src/import/client.ts → module Web Worker (src/import/worker.ts)
              └─ src/import/** — pure TypeScript: detect, decode, xer/, mspdi/, table/, checks, report
Supabase
  tables: programs · folders · project_visits (new); projects and schedules gain columns
  views:  project_summaries (recreated) · schedule_items (new)      RPCs: 15 new (§4.7)
  triggers: the §4.3 rules         storage: schedule-imports (P2 bucket) holds the original files, compressed
Map (lazy chunk): MapLibre GL JS ← one PMTiles file on Cloudflare R2 (D16)
```

- **Layer rule for the parser.** `src/import/**` imports nothing from React, `@/hooks`, `@/components`, `@/features`, `@/pages`, `@/data/mock`, `@/data/supabase` or `@/data/index`; it may `import type` from `@/data/types`. Only hooks import `src/import/client.ts`, and only `useDownloadImportReport` (§4.4) loads `src/import/csv-export.ts` and `src/import/xlsx-export.ts`, through a dynamic `import()`, so SheetJS stays out of the main chunk (S7). ESLint enforces both (our call). The parser runs unchanged in Node (tests) and later in Deno.
- **Controls for later phases** (our call, as Phase 1 did): a control whose route exists links to it even while it is a placeholder ("Open", "Open current schedule", "Import and open" → `/w/:w/p/:p/schedule?scheduleId=`); a control with no route is left out ("Compare two versions", "Share", the settings gear); nothing is shown disabled "for later". A control blocked by the state of the data (a saved version, an archived or protected schedule, someone else's lock) is a different case: it stays visible, disabled, with its reason (§6.1 "Blocked actions").
- **All new dialogs open through `useDialogs()`** (CLAUDE.md rule 5); confirmations are local `AlertDialog`s.

### 4.3 Rules both adapters enforce

Each rule is enforced by the database (constraint, trigger or RPC) and by the mock with the same code and copy; the contract tests check both. A `forbidden` refusal shows P2's generic copy "You don't have permission to do that." on both adapters, because `errorMessage()` shows adapter copy only for `conflict` and `validation` (P2 §6.1); the contract checks its code only (our call). The UI explains these cases beforehand with the tooltips of §6.4.

### 4.7 Functions, triggers and views

Every function follows the P2 rules (P2 §6.6): `p_` parameters, definer functions `security definer set search_path = ''` with qualified names, user-facing errors `check_violation` + `hint = 'app'`, permission errors `insufficient_privilege`, and per-function `revoke … from public, anon, authenticated` then `grant execute … to authenticated`. One exception, recorded in the P3 plans' Global Constraints: lock conflicts raise `lock_not_available` (55P03) with `hint = 'app'` and the R9 copy, so they map to `conflict`. Definer is used only where a function writes a column users can't write (`is_current`, lock columns, `parent_id`, `copied_from_id`, the source and import columns, `folders.parent_id`, `project_visits`) or must see rows RLS hides; the bulk functions are invoker, so RLS, column grants and the triggers below apply to them as to direct calls (D11). Every definer RPC checks the caller's role itself first, as `set_current_schedule` does.

**Role checks in invoker functions.** RLS refuses an `insert` with 42501 but only filters an `update` or `delete`: a viewer's update matches 0 rows and raises nothing (P2's `04_rls` test pins this). So every invoker RPC checks the role itself before writing, with the helper `authenticated` may execute (`app.has_role` is internal, P2 `02_privileges`): `if exists (select 1 from public.schedules s where s.id = any(p_schedule_ids) and s.project_id not in (select app.my_project_ids('editor')))` → `insufficient_privilege` (`'owner'` for `delete_schedules` and `delete_project`). After the write it compares the affected row count with the id count (after R12 adds the versions) and raises `insufficient_privilege` on a difference (defense in depth). Order in every bulk RPC: R12 count and one project → R12 all found (a select under RLS; viewers and share recipients see the rows) → R12 adds versions (archive, restore, delete) → role check → write.

## 5. Import pipeline

### 5.1 Flow

1. **Files step:** the destination project is fixed when the dialog opens from the files page, and chosen first when it opens from Home (import never creates a project); it stays visible on every step. The user adds 1–10 files at once (picker or drop); the dialog validates each one's extension and size (§6.7), then `useImportParser().inspect(file)` reads them one after another.
2. **Worker `inspect`:** reads the bytes, detects the format from the content (§5.2) and the encoding (§5.4), computes SHA-256, and returns either the projects in the file (XER, MSPDI) or the sheets, a header guess, an automatic mapping and the first 10 rows (xlsx, CSV). A refused file shows its message in its row and is left out; the others go on.
3. **Columns step** (once per xlsx or CSV file, "{file} ({i} of {k})"): the user confirms options and the mapping, or applies the columns of an earlier table import in this project (§5.7); the worker re-reads the preview on each change.
4. **Worker `analyze(mapping)`:** builds the `ImportModel` (§5.8) for one source schedule (one file, or one project of an XER), runs the checks and returns the dry-run report with up to 5,000 issues.
5. **Review step:** one row per source schedule: every XER project becomes its own row (the ones P6 flagged for export, or else the first, included by default), every other file one row. Per row the user includes or leaves it out, enters the name and code, picks "New schedule" (with a folder) or "Replace" (with a target) and, in the row's details, the activity-code field (MSPDI), the text encoding (XER) and the status date; changing any of them runs `analyze` again for that row. Rows with errors can't be included. A replace row without errors also shows the change preview of §5.13, counted again whenever its analysis or its target changes.
6. **Commit:** for each included row in turn, the worker's `pack` request returns the stored copy: the file gzipped for XER, MSPDI and CSV, whose text shrinks several times; xlsx as it is, being compressed already (our call: it keeps P2 D18's 60 s timeout workable on slow site connections). A new row calls `importSchedule`, which uploads it and inserts the schedule with `code`, `activity_count`, `import_mapping` and the report (stored issues per §5.10); a replace row calls `replaceScheduleSource` (R21). Each row is its own transaction with its own stored copy, so two projects of one XER are two objects (our call: deleting one schedule never touches another's file); one row failing doesn't undo the others. No parsed rows are written in P3 (D3). The 60 s client timeout (P2 D18) covers one upload and one write per row.
7. **Afterwards:** with one row, "Import" shows the toast "Schedule imported" with the action "View report" and opens the project's files page (D22), and "Import and open" opens the new schedule's route (a placeholder until P4, D21). With several rows, the Done step lists each row's result (§6.6), and "Close" opens the files page.

**Reload** ("Reload from original file", R21) downloads the stored original, runs `inspect` and `analyze` with the stored mapping (or the Columns step first, for a P2-era CSV), shows the Review step for that one row without the new-or-replace choice, and calls `reloadScheduleImport`. A P2-era XER has no stored `sourceProjectId`: when its file holds several projects, the Review step lists one row per project with a radio button instead of the checkbox, exactly one chosen: at first the first project P6 flagged for export, in the file's order, or the file's first project when none is flagged (step 5's default can include several projects, a radio group only one; our call), and the chosen project's `proj_id` and short name are stored as the mapping's `sourceProjectId` and the schedule's `source_project_code` (our call). For replace and reload rows, a status date left empty keeps the schedule's own (R21).

**Replace from file** (R21) runs the same steps with one file and the target fixed. One target takes one source schedule, so when that file is an XER holding several projects the Review step lists one row per project with a radio button instead of the checkbox, as Reload does, so at most one is chosen: at first the project whose `proj_id` equals the target's stored `sourceProjectId`, read with `useImportMapping(targetId)` (§4.4) (so §5.13 can match by `task_id`), or, when the target has none (a blank schedule or a copy of one, a non-XER import, a P2-era XER) or the file doesn't hold it, Reload's default above. Every row is analyzed as in step 5, so its issues show; only the chosen row is fixed to "Replace" with the target, previewed (§5.13) and imported, and the other rows are listed and not imported. A row with errors can't be chosen; when the default has errors, none is chosen at first, and replacing with none chosen shows the Review step's alert "Choose at least one schedule to import." (§6.6; our call). The chosen project's `proj_id` becomes the new mapping's `sourceProjectId`.

### 5.2 Formats and detection

The dropzone takes files named `.xer`, `.xml`, `.xlsx` or `.csv` (and names `.mpp` and `.xls` only to refuse them with their messages below). The format then comes from the content, checked in this order on the first bytes after any byte-order mark (our call, as the reference product does):

| Content | Format, or refusal message |
|---|---|
| starts with `ERMHDR` | `xer` |
| `<?xml` or `<`, root element `Project` in namespace `http://schemas.microsoft.com/project` | `mspdi` |
| XML whose root element is `APIBusinessObjects` (Primavera P6 XML) | "This is a Primavera P6 XML file. In P6, export the project as XER and import that." |
| any other XML | "This XML file isn't a Microsoft Project XML file." |
| `PK\x03\x04` with `xl/workbook.xml` in the archive | `xlsx` |
| any other zip archive | "This file isn't a readable Excel workbook." |
| `D0 CF 11 E0 A1 B1 1A E1` (a compound file) holding an `EncryptionInfo` stream | "This workbook is protected with a password. Remove the password in Excel, save it and import it again." |
| a compound file named `.mpp`, or holding Microsoft Project streams | "MPP files can't be imported. In Microsoft Project, save the file as XML and import that." |
| any other compound file (an `.xls` workbook among them) | "Older Excel workbooks (.xls) can't be imported. In Excel, save the file as .xlsx and import that." |
| starts with `SQLite format 3` | "This is a database file, not a schedule export. Export the project as XER from P6 or as XML from Microsoft Project." |
| text in a supported encoding, in a file named `.csv` | `csv` |
| anything else | "This file type can't be imported. Use a P6 XER, a Microsoft Project XML, an Excel .xlsx or a CSV file." |

A supported format in a file whose extension names another (an XER saved as `.csv`, MSPDI as `.xer`) is read as what it holds, with `FORMAT_FROM_CONTENT` (our call — beyond the reference: the reference product refuses such a file, but nothing is gained by making the user rename it). A file that passes this check but can't be read through (cut short, `%R` before `%F`, malformed XML, nesting deeper than 100 levels, a workbook part SheetJS can't parse) gives `FILE_UNREADABLE`. An xlsx is the one exception, because its container is checked before its content: an archive that can't be inflated through safely (cut short, a broken entry, or past the zip guard's limits, §5.10, §5.11) is refused with "This file isn't a readable Excel workbook.", the message of the "any other zip archive" row above, and never reaches a report (D61, D69: one message for every workbook we can't open safely). The parser's entry points catch everything: any file gives a report or a pinned message, never an exception or a hang (§7). Database connections are not a source: P3 imports files only.

### 5.3 Where parsing runs

- **A module Web Worker** (`new Worker(new URL('./worker.ts', import.meta.url), { type: 'module' })`), started by `useImportParser` when the dialog opens and terminated when it closes. It keeps the file's bytes between `inspect`, `analyze` and `pack`.
- **Protocol** (`protocol.ts`): `inspect`, `preview`, `analyze`, `pack`, `compare` (P3d, §5.13), `cancel`; each request carries an id; responses are `{ ok: true, result } | { ok: false, issue }`. Results are plain JSON, except `pack`'s bytes, which are transferred; `compare`'s request transfers the target's original bytes into the worker, which discards them after the answer.
- **Watchdog:** 30 s per request; on expiry the client terminates the worker and reports "This file took too long to read. Try a smaller export." Edge Functions are not used: their CPU limit is far below what a 20 MB file needs.
- **Fallback:** where `Worker` is missing (jsdom), `client.ts` runs the same functions in the calling thread; tests use this path.

### 5.4 Encoding, numbers, durations and dates

- **Encoding (XER, CSV):** a byte-order mark decides (UTF-8, UTF-16 LE/BE) and can't be overridden. Otherwise `TextDecoder('utf-8', { fatal: true })` succeeding means UTF-8. Otherwise, when at least one multi-byte sequence is valid UTF-8 and at least 99 % of the bytes above `0x7F` belong to valid sequences, the file is UTF-8 and the rest become U+FFFD (`ENCODING_INVALID_BYTES`; our call: a UTF-8 export with one pasted Windows-1254 note stays UTF-8). Otherwise a single-byte page is chosen by scoring bytes `0xD0 0xDD 0xDE 0xF0 0xFD 0xFE` (Turkish letters in Windows-1254) and `0x8E 0x9E` (Windows-1252 only), defaulting to Windows-1254 (`ENCODING_GUESSED`), which also reads ISO-8859-9 files (the Encoding Standard maps that label to Windows-1254). The detected value and how it was found go into the report; the user can override any encoding not set by a byte-order mark: CSV in the Columns step, whose preview shows the decoded names, and XER in the Review step, which shows the first five activity names as decoded so wrong letters (ç ğ ı İ ö ş ü) are seen before importing (our call — beyond the reference). MSPDI uses its XML declaration. xlsx needs none.
- **Numbers (CSV, xlsx text cells):** the decimal separator is guessed per file from a sample (`2,5`, `1.234,5`) and confirmed in the Columns step. Grouping separators are removed only when the other separator is the decimal one. A `%` sign is dropped; xlsx number cells whose format contains `%` are multiplied by 100 (0.5 → 50).
- **Durations (tables, `durations.ts`):** a number with an optional unit, spaces allowed, in English or Turkish: minutes (`m`, `min`, `dk`, `dakika`), hours (`h`, `hr`, `hrs`, `hour`, `hours`, `sa`, `saat`), days (`d`, `day`, `days`, `g`, `gün`), weeks (`w`, `wk`, `wks`, `week`, `weeks`, `hf`, `hafta`) and months (`mo`, `mon`, `mons`, `month`, `months`, `ay`). A day is `hoursPerDay` hours, a week 5 days and a month 20 days (Microsoft Project's defaults). A number without a unit uses the Duration unit option. A trailing `?` (Microsoft Project's estimate mark) is dropped (`TABLE_ESTIMATED_DURATION`); an `e` before the unit (`2 edays`, `3 egün`) is elapsed time (`ELAPSED_DURATION`). Anything else is `TABLE_BAD_DURATION`.
- **Dates:** source timestamps are wall-clock times without a zone and are parsed by regex into `'YYYY-MM-DDTHH:mm'` strings, never with `new Date(string)`. XER accepts `yyyy-M-d[ H[:mm[:ss]]]`; MSPDI `yyyy-MM-ddTHH:mm:ss`. Table cells use the chosen `ImportDateFormat` for the order of day, month and year, and accept one- or two-digit days and months, four- or two-digit years (two digits → 20yy), an optional weekday name in front in English or Turkish (`Mon`, `Monday`, `Pzt`, `Pazartesi`, …), month names in English or Turkish, full or three letters, in the month's place (`15 Mart 2026`), and an optional time (`08:00`, `8:00 AM`); or real xlsx dates (1900 system including the false 29 Feb 1900, or 1904, read from the workbook). Date-only cells take the times of `TableAssumptions`.
- **Matching (`foldForMatch` in `src/lib/search.ts`):** `trim()`, `toLocaleLowerCase('tr')`, then `ı` → `i`, then canonical decomposition with the combining marks removed (`ç` → `c`, `ğ` → `g`, `ö` → `o`, `ş` → `s`, `ü` → `u`, `â` → `a`). Turkish lower-casing turns capital I into dotless ı, so without the `ı` step "Activity ID" would never match the alias "activity id". With it, headers such as "ID", "Activity ID" and "İŞ KODU" match lower-case aliases, and in search "it" finds "IT block", "istanbul" finds both "İSTANBUL" and "ISTANBUL", and "insaat" finds "İnşaat" (our call — beyond the reference, whose search knows neither). Header aliases, activity type values, constraint names and every search box use it (our call). Sorting keeps P2 D21's collator.

### 5.5 XER

- Tables are read by their `%F` field names into `Object.create(null)` records; unknown fields are ignored, missing optional fields are tolerated; a record whose first token is empty continues the previous one; `%E` ends the file. `CALENDAR.clndr_data` is a nested `(key|value(…)())` structure whose entries may be separated by line breaks or `0x7F` characters; both are accepted (V12 checks real exports).
- **Several projects:** each project in the file is its own row in the Review step ("{proj_short_name} · {name}"), and each included one becomes its own schedule (§5.1); by default the projects with `export_flag` set are included, or the first when none is. Each row reads only its project's WBS, activities and links; links to another project in the file or outside it are skipped (`XER_CROSS_PROJECT_LINK`) and counted per other project in `externalLinks`. Global and project calendars the project uses are read; resource calendars are read into the model as `kind: 'resource'` and never assigned to activities.
- **Schedule level:** the project's short name, name and code, the name of its root WBS node (`sourceProject.rootWbsName`), the data date `PROJECT.last_recalc_date` as the status date, the must-finish-by date, the project's default calendar, the stated start and finish, and in `settings`: the progress mode (retained logic, progress override or actual dates), `sched_calendar_on_relationship_lag` (D40) and the four resource unit and cost calculation flags, kept as written (P4 uses two; the others only matter for a later XER export). V12 confirms each field name on real exports.
- **Mapping:** `PROJWBS` → WBS (code, name, tree by `parent_wbs_id`, order `seq_num`, the project node skipped as a level but kept as `rootWbsName`); `TASK` → activities, code `task_code` (a code used twice: `DUPLICATE_CODE`), source key `task_id`; `task_type` `TT_Task` → task, `TT_Rsrc` → task on its own calendar (`XER_RESOURCE_TASK`), `TT_Mile` → start milestone, `TT_FinMile` → finish milestone, `TT_LOE` → level of effort, `TT_WBS` → WBS summary; status, physical % (a manual value) and the % complete type; original and remaining duration; actual, early, late and remaining (restart and re-end) dates; total and free float as written (§5.8); `TASKPRED` `PR_FS/SS/FF/SF` with `lag_hr_cnt`, positive or negative; an unknown link type becomes FS (`LINK_TYPE_UNKNOWN`); constraints `CS_MSO`, `CS_MSOA`, `CS_MSOB`, `CS_MEO`, `CS_MEOA`, `CS_MEOB`, `CS_MANDSTART`, `CS_MANDFIN`, `CS_ALAP` and none (as soon as possible), primary and secondary, each with its date; `clndr_data` parsed for the work week (days 1–7, 1 = Sunday; several periods a day; 24-hour and `h:mm AM` shift times) and exceptions (`d|<days since 1899-12-30>`); each calendar's hours per day, week, month and year.
- **Expected finish** is not used (P4's engine doesn't support it): activities with an expected finish date give one `XER_EXPECTED_FINISH` warning with their count. Baselines held in the file (other projects marked as baselines) are never turned into tags; the baseline is chosen on the files page.
- **Calendar inheritance:** a calendar with `base_clndr_id` inherits the exceptions of its base that it doesn't define itself, resolved down the chain (cycle-safe, at most 5 levels); a base that isn't in the file gives `CALENDAR_BASE_MISSING`. A task with no `clndr_id`, or one not in the file, uses the project's `clndr_id` (`CALENDAR_MISSING`).
- **Units:** hours become working minutes with the activity's calendar; a calendar whose `day_hr_cnt` disagrees with its work week uses the work week (`CALENDAR_HOURS_MISMATCH`).
- **Calendar problems** (our call, as the reference product does, D47): a calendar that the project, an activity or another used calendar needs and that can't be read completely (unreadable data, a missing base) stops the import with an error naming it (`CALENDAR_UNREADABLE`, `CALENDAR_BASE_MISSING`); the same problem in a calendar nothing uses is a warning and the calendar is skipped (`CALENDAR_UNUSED_SKIPPED`). No calendar is ever replaced with a standard week.
- **Counted, not read in P3:** RSRC, RSRCRATE, TASKRSRC, ACTVTYPE, ACTVCODE, TASKACTV, UDFTYPE, UDFVALUE, TASKMEMO, CURRTYPE and any other table (listed in `notImported`; activity codes, user-defined fields, resources and assignments wait for P5, D39).

### 5.6 MSPDI

- `fast-xml-parser` with `parseTagValue: false`, `processEntities: false`, `removeNSPrefix: true` and `isArray` for `Task`, `PredecessorLink`, `Calendar`, `WeekDay`, `WorkingTime`, `Exception`; values are converted explicitly. With entity processing off the library leaves `&amp;` and character references as written, so `mspdi/xml-text.ts` decodes the five predefined entities and decimal and hex character references in every text value we read; a reference to U+0000, a surrogate or a code point above U+10FFFF becomes U+FFFD (`XML_BAD_CHARACTER`) instead of throwing (our call; "Kazı &amp; Dolgu" imports as "Kazı & Dolgu").
- **Tasks:** `Summary = 1` tasks become WBS elements (tree from `OutlineLevel` in file order; the project summary task UID 0 skipped; code = the last segment of `OutlineNumber`, our call as the reference product does); values stored on summary rows are not read. Other tasks become activities with their GUID kept as a source key. Skipped and reported: `IsNull` rows with their links, inactive tasks (`MSPDI_INACTIVE_TASK`), external tasks and inserted subprojects (`ExternalTask = 1` or `IsSubproject = 1`, `MSPDI_EXTERNAL_TASK`), links on summary tasks, external and cross-project links (counted per target in `externalLinks`). Our call, unlike the reference product, which keeps inactive and external rows as ordinary activities: an inactive task kept as an activity would drive its successors, which it doesn't do in the source.
- **Status** (our call, as the reference product does): an actual finish means completed; else an actual start means started; else `PercentComplete` ≥ 100 means completed and > 0 started; else not started. `PercentComplete` is kept as duration % and `PhysicalPercentComplete` as physical % (the reference product files the first as physical %; we keep each where the source put it); % work complete is not read.
- **Activity codes:** `UID` by default (stable when rows are inserted, so codes match across updates). The Review step's "Activity codes" also offers "ID" (the row number Microsoft Project shows, which the reference product uses; it shifts when rows are inserted, so a hint warns about matching later updates) and each `Text1`–`Text30` field filled and unique on at least 90 % of activities (stored as `activityCodeField`). With a Text field chosen, an activity whose value is empty or shared with another activity uses its UID instead (`CODE_FALLBACK`); codes are then shortened to 40 characters (`TEXT_TRUNCATED`), and a code still used twice is `DUPLICATE_CODE`, an error as in every format (our call).
- **Dates and floats:** start, finish, early and late dates (early and late fall back to start and finish when blank), actual dates, `Stop` and `Resume` as the remaining window, total and free slack as written (§5.8: kept, never used for dates).
- **Milestones** (our call, as the reference product does, D48): a zero-duration task (flagged or not) is a start milestone when its time of day is the first working minute of its calendar's day, and a finish milestone when it is the last; any other time is ambiguous, becomes a start milestone and gives `MSPDI_MILESTONE_AMBIGUOUS`. `Milestone = 1` with a duration → task (`MSPDI_MILESTONE_WITH_DURATION`); zero duration without the flag also gives `MSPDI_ZERO_DURATION`.
- **Manually scheduled tasks** (as the reference product does): a task with no constraint gets "start on or after" at `ManualStart`, or at `Start` when that is blank (`MSPDI_MANUAL_TASK`); a task with a constraint keeps it and its manual start is dropped (`MSPDI_MANUAL_START_DROPPED`). Manual finish and text durations are not read.
- **Durations:** working time on the task's calendar; an elapsed `DurationFormat` (the "e" units) gives the activity a 24-hour, 7-day calendar added to the model (`ELAPSED_DURATION`).
- **Links:** `Type` 0 FF, 1 FS, 2 SF, 3 SS (anything else → FS, `LINK_TYPE_UNKNOWN`); `LinkLag` in tenths of a minute, stored as minutes; elapsed lag formats keep a 24-hour lag calendar (`ELAPSED_LAG`; our call — beyond the reference, which turns them into working time); percentage lags become working time of the predecessor's duration, once (`PERCENT_LAG`).
- **Constraints:** 0 none, 1 as late as possible, 2 mandatory start, 3 mandatory finish, 4 start on or after, 5 start on or before, 6 finish on or after, 7 finish on or before; one per activity. Deadlines are not read (`outcomes`).
- **Calendars:** `WeekDays` (DayType 1–7 = Sunday–Saturday, several periods a day; DayType 0 legacy exceptions) and 2007+ `Exceptions` (single days, date ranges, custom working hours) with recurrences (daily, weekly, monthly or yearly, on a fixed date or a relative weekday) expanded to dates from the schedule's start to 20 years after its finish, at most 10,000 dates per calendar (`CALENDAR_RECURRENCE_CAPPED`); `WorkWeeks` → default week only (`MSPDI_WORK_WEEKS`). A derived calendar (`IsBaseCalendar = 0` with a `BaseCalendarUID`) lists only what differs from its base: it inherits every weekday and exception it doesn't list, resolved down the chain (cycle-safe, at most 5 levels). A task's `CalendarUID` of -1, or none, means the project calendar (`Project/CalendarUID`); task and resource calendars keep their assignments in the model. Durations use the project's `MinutesPerDay` (default 480) as MS Project does; it is recorded in `units`. Unreadable data, a recurrence we can't expand (`CALENDAR_RECURRENCE_UNSUPPORTED`) or a missing base follow the calendar-problem rule of §5.5: an error naming the calendar when something uses it, a skipped calendar otherwise.
- **Project level:** name, start, finish (`sourceProject.stated`), status date and project calendar. **Settings kept for P4:** `ScheduleFromStart`, `CalendarUID`, `MinutesPerDay`, `MinutesPerWeek`, `DaysPerMonth`, `DefaultStartTime`, `DefaultFinishTime`. Currency, fiscal-year, critical-slack, default task type and earned-value settings are not read (`outcomes`).
- **Status date:** `StatusDate`; when absent or invalid the Review step's field is filled with the earliest task start and says so (`STATUS_DATE_FALLBACK`, as the reference product does); the user can change it.
- **Not read** (each listed in `outcomes` with its count): recurring task definitions, leveling and priority, hyperlinks, custom and enterprise fields, outline codes, baselines, costs, earned-value fields, timephased data and split segments. Task notes are read (our call — beyond the reference).

### 5.7 Excel and CSV: the Columns step

- **Reading:** CSV through Papa Parse on the decoded text with the chosen or detected delimiter (the candidate among `,` `;` tab that gives the most rows with a constant field count; shown and changeable). xlsx through SheetJS with `dense: true`, `cellFormula: false`, `cellDates: false` (serials are converted by §5.4), `sheets` limited to the chosen sheet and `sheetRows` 20,051; hidden rows are read, merged cells take the top-left value.
- **Options** (defaults from detection): Sheet, Header row (1–50), Text encoding (CSV), Delimiter, Decimal separator, Date format, Duration unit (Days / Hours, for numbers without a unit), Hours per day (1–24, default 8), Predecessors refer to ("Activity code" or "Task ID"; "Task ID" by default when the Task ID field is mapped), Rows with problems ("Import them, leaving bad cells empty" by default, or "Skip them"; `skipRowsWithIssues`, as the reference product's per-row exclusion; a skipped row is counted and named by `TABLE_ROW_SKIPPED`).
- **Earlier mappings** (our call — beyond the reference): when one of the project's last five table imports (`listTableMappings`) mapped headers that all appear in this file's header row, the step offers "Use the columns from {schedule name}", which applies that mapping's options and columns by header name. Saved mapping templates per workspace were deferred by the owner (D67, §2.3).
- **Fields:** Activity code and Activity name are required; Task ID (the row number Microsoft Project writes in its "ID" column, used only to resolve predecessors), WBS (a code, or a path split on `.`, `/` or `>`), Duration, Start, Finish, Actual start, Actual finish, Activity type, Calendar (a name; every distinct name becomes a calendar with the default work week of `TableAssumptions`, reported), Constraint, Constraint date, % complete, Predecessors and Notes are optional. Each column maps to at most one field.
- **Automatic mapping:** each field has English and Turkish header aliases in `auto-map.ts`, compared with `foldForMatch` (our own word lists, e.g. code: "activity id", "unique id", "code", "kod", "aktivite kodu"; Task ID: "id", "kimlik"; name: "activity name", "task name", "name", "ad", "aktivite adı"; duration: "duration", "süre"; start: "start", "başlangıç"; finish: "finish", "bitiş"; predecessors: "predecessors", "öncüller").
- **Values:** numbers, durations and dates as §5.4; % complete 0–100 after §5.4 (anything else `TABLE_BAD_NUMBER`).
- **Activity type values** accepted (case-insensitive): task, milestone / start milestone, finish milestone, level of effort, and Turkish "görev", "kilometre taşı"; anything else → task (`TABLE_UNKNOWN_TYPE`).
- **Constraint values** (`constraints.ts`, compared with `foldForMatch`): the app map's names ("Start on", "Start on or after", "Start on or before", "Finish on", "Finish on or after", "Finish on or before", "Mandatory start", "Mandatory finish", "As late as possible"), which P6 also uses; Microsoft Project's names and abbreviations: "As soon as possible" / "ASAP" → no constraint, "As late as possible" / "ALAP", "Must start on" / "MSO" → mandatory start, "Must finish on" / "MFO" → mandatory finish, "Start no earlier than" / "SNET" → start on or after, "Start no later than" / "SNLT" → start on or before, "Finish no earlier than" / "FNET" → finish on or after, "Finish no later than" / "FNLT" → finish on or before; and the Turkish names V11 records. Anything else → `CONSTRAINT_UNSUPPORTED`.
- **Predecessors cell:** tokens separated by `;` (or `,` when the decimal separator is `.`), each `<ref> [type] [lag]` with spaces allowed between the parts. `<ref>` is an activity code or a Task ID ("Predecessors refer to"); type `FS`, `SS`, `FF` or `SF` (default `FS`); lag `+` or `-`, a number and an optional unit as for durations, or a percentage converted like MSPDI's (`PERCENT_LAG`). Examples: `A100FS+2d; A120SS`, `3FS+2 days`, `12SS-1 hafta`, `7FS-25%`. Unknown references, self-links, duplicates and unreadable tokens are skipped and reported.
- **Preview:** the first 10 data rows with mapped columns emphasized and invalid cells marked; the issues come from the same normalizer as `analyze`.
- Duplicate activity codes are **errors** (`DUPLICATE_CODE`; P4 and P6 match activities by code).
- V11 records how Microsoft Project's Turkish build writes link types, lags, durations, dates and constraint names in its Excel and CSV exports (or, when the owner's Turkish export comes from another tool, how that tool writes them); its tokens join the alias lists.

### 5.8 What P3 stores, and what P4 does with it

`ImportModel` (in `src/import/model.ts`, not part of the repository contract): `project` (code, name, root WBS name, stated start and finish, must-finish-by, default calendar), `calendars` (id, name, kind `project` / `global` / `resource` / `task`, work week as minutes per weekday with several periods, exceptions, hours per day, week, month and year, after inheritance), `wbs` (id, parentId, code, name, order), `activities` (source keys — XER `task_id`, MSPDI `UID` and `GUID` — code, name, wbsId, type, calendarId, original/remaining duration in working minutes, planned, early, late, actual and remaining-window start/finish strings, primary and secondary constraint with dates, physical and duration % with the % complete type, status, source total and free float in working minutes, notes, flags such as `manual`), `relationships` (predecessor and successor codes, type, lag in working minutes, lag calendar as the source defines it, D40), `settings`. Source floats and early and late dates are kept for display and for comparing with P4's first calculation, never used as inputs (the `outcomes` catalog says so). P3 uses the model for counts, checks and the report only (D3).

P3 stores on the schedule: the original file (P2 bucket, compressed, §4.9), `source_format`, the original's size and SHA-256, `source_project_code`, `parser_version`, `import_mapping`, `import_report`, `activity_count` and the status date. Parsing is deterministic: the same bytes and mapping always give the same model, and golden `*.model.json` files pin it for every fixture.

**P4 hand-over.** What P3 guarantees:

- The stored original is never changed: the bucket has no update policy, users can't update `source_file_path` (only `replace_schedule_source` moves the old object to the saved version it creates), and only owners (or the uploader, for an unreferenced object) can delete it (§4.9).
- An imported schedule arrives protected (R17), so its dates stay the source tool's until someone removes protection; the confirmation then says that recalculating may move forecast dates and never changes actual dates (§6.4). P4 keeps that promise.
- `import_mapping` holds every choice the user made and, for tables, the fixed `TableAssumptions` (what Duration, Start / Finish and % complete mean, the times of date-only cells, the length of a week, the default work week), so P4 reads a P3 table import without asking again.
- `src/import` runs in Node and in the browser and gives the golden-tested `ImportModel`.

What P4 decides: how stored imports become its tables. Not every reader can do it: viewers can't write, share recipients can't read `schedule-imports` (P2 storage policy), and Edge Functions are too slow (§5.3). The candidates are materializing on the first open by an editor (others see a "not ready yet" state) or a one-off Node script with the service key, run from the runbook and reusing `src/import`. P4 also adds the grants or functions it needs to refresh `import_report` and `activity_count` (P3 grants no update on them; P3's own changes go through replace and reload), and, before it reads a P2-era import nobody reloaded, asks for what P2 didn't record: a column mapping for a CSV, the source project for an XER holding several projects (§4.6, §5.1).

### 5.9 Import report

The report (§4.1 `ImportReport`) is shown as the dry run in the Review step and stored with the schedule; the Import report dialog shows the stored one. Everything the dialog and the downloads show comes from the report alone (the "Activity codes" line from its `activityCodeField`); the Review row's "First activities" and "Changes to {target}" aren't in the report, so the dialog and the Excel "Summary" leave them out (§6.6). Downloads: "Download CSV" (one row per issue: severity, code, message, location, original, used; cells that start with `=`, `+`, `-`, `@`, tab or CR, including full-width forms, get a leading `'` and every cell is quoted), "Download Excel" (below; D65) and "Download JSON" (the report object). File names: `{schedule name} - import report.csv` / `.xlsx` / `.json`, where the Review step uses the row's Name field. All three go through `useDownloadImportReport` (§4.4). Issue texts (`message`, `location`, `original`, `used`) are at most 200 characters, cut with "…", in the dry run and the stored report. The stored report keeps fewer issues (§5.10); `issueTotals` stay exact and the dialog says so (§6.6).

**Excel download** (P3d; D65, the owner's improvement (b)). `src/import/xlsx-export.ts` exports `reportToXlsx(report, scheduleName) → Uint8Array`, written with the SheetJS already in P3 (`utils.aoa_to_sheet`, `write` with `bookType: 'xlsx'`, `type: 'array'`), pure and unit-tested. The workbook has these sheets, in this order, each with its header row even when it has no other rows:

| Sheet | Columns | Rows |
|---|---|---|
| "Summary" | "Item" · "Value" | "Schedule" ({schedule name}), then the Review row details' lines in their order and with their labels, each read from the report (§6.6: "File", "Format", "Activity codes" from `activityCodeField` as "Unique ID", "ID" or the Text field's name, "Text encoding", "Status date", "Dates"; lines that don't apply to the format left out, so "Activity codes" appears for MSPDI only), then "Parser version", "SHA-256", "Errors", "Warnings", "Notes" (from `issueTotals`), "Issues listed" (the number of rows on "Issues"), then `breakdown` as "Activities: {type}", "Started", "Completed", "Relationships: {type}", "Constraints", "Calendar exceptions", then one "Setting: {key}" row per `settings` entry |
| "Counts" | "Element" · "Read" · "Accepted" · "Adjusted" · "Skipped" | "Calendars", "WBS elements", "Activities", "Relationships" |
| "Checks" | "Check" · "Findings" | the nine checks by their §6.6 names, zeros included |
| "File contents" | "Element" · "Outcome" · "Items" | `outcomes`, the outcome as "Used for dates", "Kept for display and export" or "Not read; still in the original file" |
| "Not imported" | "Table" · "Rows" | `notImported` |
| "External links" | "Target" · "Links" | `externalLinks` |
| "Issues" | "Severity" · "Code" · "Group" · "Message" · "Location" · "Original" · "Used" | one row per issue in the report's order; severity "Error", "Warning" or "Note"; the group title of §5.12 |

Text goes into string cells and counts into number cells; dates are ISO text (`YYYY-MM-DD`, with ` HH:mm` when the report holds a time), which no spreadsheet locale misreads; the workbook has no formulas, no styles and no document properties (no author name). A string cell is never evaluated, so the CSV's leading `'` isn't added (V1 confirms that Excel and LibreOffice show a cell holding `=1+1` as text). SheetJS is loaded only through the hook's `import()` (§3, S7).

**Count rules** (Goal 3), per entity in `counts`: `read = accepted + skipped`; `adjusted ≤ accepted` (an adjusted item is accepted with a change, such as a shortened name or a fallback code); every skipped or adjusted item has at least one issue naming it. A parser test asserts them for every fixture.

**Summary** (`breakdown`, as the reference product's post-import summary): activities by type, milestones among them, activities started and completed, relationships by type, constraints and calendar exceptions, over accepted items; with `counts`, the status date and `dateRange` it is shown before the import is confirmed and kept afterwards. `dateRange` is the accepted activities' span as written in the file, before any recalculation; the `project_dates_differ` check compares it with the dates the file states for the project.

**What happened to each part of the file** (`outcomes`; our wording for the reference product's three outcomes): `src/import/outcomes.ts` holds a fixed catalog per format of every source element we know (for XER by table and field group, for MSPDI by element, for tables by mapped field), each with one outcome: **used** ("Used for dates": durations, logic, calendars, constraints, actual dates), **kept** ("Kept for display and export": source floats, early and late dates, notes, settings P4 doesn't apply), or **not read** ("Not read; still in the original file": resources, codes, user-defined fields, costs, baselines, deadlines, the settings §5.6 lists). The report lists the elements present in the file with the number of items carrying them. Our improvement on the reference product: "not read" never means lost, since the original stays with the schedule (§5.8).

**Checks** (our call — beyond the reference, which leaves this checklist to the user): `checks.ts` runs every check below on every import and records each one's number of findings, zeros included; each finding is also an issue. `actual_after_status_date` (`ACTUAL_AFTER_STATUS_DATE`), `progress_without_actual_start` (`PROGRESS_WITHOUT_ACTUAL_START`), `complete_without_actual_finish` (`COMPLETE_WITHOUT_ACTUAL_FINISH`), `status_date_fallback` (`STATUS_DATE_FALLBACK`), `ambiguous_milestones` (`MSPDI_MILESTONE_AMBIGUOUS`), `percent_lags` (`PERCENT_LAG`), `links_on_summaries` (`MSPDI_SUMMARY_LINK`), `external_links` (`XER_CROSS_PROJECT_LINK`, `MSPDI_EXTERNAL_LINK`), `project_dates_differ` (`PROJECT_DATES_DIFFER`). A dry-run recalculation that previews how forecast dates would move is P4's.

**Issues** are grouped by code in the Review step and the report dialog: one row per code with its group title (§5.12) and count, expanding to every issue of that code with its message and location (as the reference product's warnings open a list of the affected items).

**Fatal errors** (any `error` issue) stop that row's import with no partial result. The Review step and the Files step's refusals offer "Copy details", which copies the message, code, file name, size, detected format and parser version as plain text for support (our call — beyond the reference) → toast "Details copied".

### 5.11 Security

- Compound files (§5.2) are recognized from their header and directory entry names only; nothing inside them is parsed.
- Any XML with `<!DOCTYPE` is refused before parsing ("This XML file isn't a Microsoft Project XML file."); the library expands no entities, and `xml-text.ts` decodes only the predefined ones and character references (§5.6); `fast-xml-parser` is at least 5.3.5, which V2 confirms carries the fixes for the 2026 advisories on out-of-range numeric entities (an uncaught `RangeError`) and DOCTYPE entities overriding the built-in ones.
- xlsx: `zip-guard.ts` doesn't trust the sizes an archive declares. It streams every entry through `fflate`'s `Unzip`, counts the real inflated bytes, discards them and aborts past a limit (§5.10), refusing the file with the §5.2 message "This file isn't a readable Excel workbook."; an archive that ends early or holds an entry that can't be inflated is refused with the same message (D69); only then does SheetJS read the archive, whose sizes are now known. The 30 s watchdog stops anything left; the worker isolates the parse from the page's state (a memory blow-up may still affect the tab, accepted).
- Records keyed by names taken from the file use `Object.create(null)` or `Map` (`safe-record.ts`); `settings` is a key/value array.
- Names, notes and messages are rendered as React text only; no `dangerouslySetInnerHTML` anywhere in P3.
- The server trusts nothing: column checks bound sizes and enums; the stored-file path is checked against the row's project and kept unique (§4.9); the report is the uploader's own description of the file, and P4 rebuilds data from the stored original, never from the report.
- Fixtures are our own files written by hand or by `scripts/make-xlsx-fixtures.ts`; no vendor sample files (IP rule). Real exports are used only as D68, V11 and V12 describe: kept in the git-ignored `real-exports/` folder of the main checkout, read locally by path (never copied into a worktree), never committed, not even as anonymized copies.

### 5.13 Replace preview (P3d)

The owner's improvement (a) (D64): before "Replace from file" puts a new file under a schedule, the Review step counts the activities the file adds, removes and changes compared with the schedule's current content. The preview informs and never blocks: the replace's saved version keeps the previous content anyway (R21).

- **The two sides.** "After" is the replace row's `ImportModel` from its latest `analyze` (a row with errors gets no preview). "Before" is the target's current content, which in P3 is its stored original read again with today's parser and the target's stored mapping: `useReplacePreview` (§4.4) calls `getImportMapping` and `getScheduleSourceFile` and sends the bytes and mapping to the worker's `compare` request, which reads them as `analyze` would and compares the two models. A target with no original file (a blank schedule, or a copy of one) has no activities in P3: it is compared with an empty model without fetching anything (`before.source = 'blank'`), so every activity is added.
- **Unavailable** (`ReplacePreviewResult`; §6.6 names the reason and the replace stays allowed): `no_original` when the original can't be downloaded (a storage error, or demo mode after a page reload, §4.5); `no_mapping` when a P2-era import lacks a mapping it needs (a CSV, or an XER holding several projects, §4.6); `unreadable` when reading the original gives a §5.2 refusal or any error issue. A P2-era XER holding one project and a P2-era MSPDI are read with the defaults (the detected encoding, `UID` as the code field).
- **Matching** (`src/import/compare.ts`, pure, D64). First by source key, only between two files of the same format: XER by `task_id` when both mappings name the same `sourceProjectId` (a `task_id` belongs to one P6 database, so a project exported again from another database matches by code instead); MSPDI by `GUID` when every activity on both sides has one (Microsoft Project 2010 and later write them), else by `UID`. Tables have no stable key (a Task ID is a row number) and files of different formats share none, so they match by code only. Then, among the activities still unmatched, by equal activity code. Each activity is matched at most once and the code pass never undoes a key match; keys and codes are unique in a model without errors (`DUPLICATE_CODE` is an error), so the result doesn't depend on order. `matchedBy` lists the keys used for the pair, in this order: `task_id` then `code`; `guid` or `uid`, then `code`; or `code` alone.
- **Changes.** A matched pair is **changed** when any of these differs, else **unchanged**: `code`; `name`; `wbs` (the path of WBS codes); `type`; `calendar` (its name); `duration` (original or remaining, in working minutes); `planned_dates` (planned start or finish); `actual_dates` (actual start or finish); `progress` (status, duration % or physical %); `constraint` (primary or secondary, type or date); `logic` (its set of predecessor links, each as the predecessor's match, type and lag; a link to an added or removed activity counts). `changedBy` counts each field once per activity. Only a key match can change the code, so the `code` entry counts activities that kept their source key under a new code.
- **Sums** (asserted for every fixture pair, S11): `before.activities = removed + changed + unchanged`; `after.activities = added + changed + unchanged`; the `matchedBy` counts add up to `changed + unchanged`.
- **Low match.** When `before.activities > 0` and either fewer than half of them are matched or more than half of the matched pairs changed their name, the Review step shows a warning line (§6.6): a wrong target is the likeliest mistake in a monthly replace, and the name test also catches keys that match by coincidence.
- **Budget and determinism.** Comparing two 10,000-activity models takes under 1 s (3 s on CI runners), a budget test beside S5's; the 30 s watchdog of §5.3 covers the whole request. The same inputs always give the same preview; golden `*.preview.json` files pin it for each fixture with a second version (XER, MSPDI and the UTF-8 CSV, which matches by code only), compared with its first. The XER's second version holds the same two projects (the same `proj_id`s), so the Replace dialog's project choice (§5.1) is exercised; its golden preview compares the first project's two versions.
- **Never stored.** The preview is counted again whenever the row's analysis or target changes and is not saved with the schedule; the saved version keeps the previous content, and P6's version diff compares the two in detail with the same matching (§2.3).

### 6.3 Map layout

The roadmap's P3 row names a map layout and §3 names MapLibre GL JS "with a tile provider whose usage policy allows production", so the layout ships. The owner decided on 2026-11-03 (D16): OpenStreetMap-based map data and its required credit are an approved exception to the IP rule; the tiles are hosted on Cloudflare R2 under a custom domain on the app's own domain in Cloudflare; the map covers Türkiye to zoom 15 plus a low-zoom world layer to zoom 6.

- **Library and tiles:** MapLibre GL JS in a lazy chunk; one PMTiles file on Cloudflare R2 under a custom domain on the app's domain, which the owner manages in Cloudflare (R2's `r2.dev` address is rate-limited and not meant for production), read with HTTP range requests. The file holds Türkiye up to zoom 15 plus a world layer up to zoom 6, so projects abroad still sit on a map (two sources if V6 finds one file impractical). The bucket uses the EU jurisdiction and a CORS rule that allows only the app's origins. Label glyphs: the OFL-licensed Noto glyph files from Protomaps' `basemaps-assets`, hosted beside the tiles (no font tool in the repo). Our own style built with `@protomaps/basemaps` layers whose colors come from the CSS tokens at runtime (light and dark), without the `landcover` layer (its ESA WorldCover data would need another credit), with no point-of-interest icons and no sprites. Config: `VITE_MAP_PMTILES_URL`, `VITE_MAP_GLYPHS_URL`; `public/_headers` `connect-src` names the tiles host exactly, pinned in `scripts/headers.test.mjs`; MapLibre's CSP worker build is served from our origin (`setWorkerUrl`).
- **Owner task before the map task** (in P3e): create the bucket and its custom domain, set the CORS rule, upload the tiles and glyphs, and send the two URLs. Until the URLs are configured, the layout shows its "Map unavailable" state (States below).
- **Attribution** (the credit the IP-rule exception requires, D16): "© OpenStreetMap contributors" linking to `https://www.openstreetmap.org/copyright`, always visible. It is our own element over the map's corner (MapLibre's attribution control is turned off), so component tests can find it while `maplibre-gl` is mocked; no MapLibre or third-party logo.
- **Content:** a region with aria-label "Project map"; one marker per filtered project with coordinates (a button, 28 px, `bg-primary`, `MapPin` 16 in `text-primary-foreground`, aria-label "{project name}"); opening it shows a popup with name, code chip, `StatusBadge`, city and the link "Open project". The view fits the markers (padding 48, max zoom 12), else Türkiye. No clustering (our call; clustering, choosing a location by clicking the map, filtering by the visible area and province and district lists were deferred by the owner, D67, §2.3). Beside the map (below it under 1024 px), a panel "Not on the map ({n})" lists the filtered projects without coordinates, each with "Add location" for editors → `editProject` at the Location step, so no project is left out silently.
- **States:** no project has coordinates → overlay "No project has a location yet." / "Add latitude and longitude in Edit project."; `VITE_MAP_PMTILES_URL` unset or tiles fail → `EmptyState` `MapPinOff`, "Map unavailable" / "Map tiles aren't set up for this deployment." (the panel stays).
- **Tests never call R2:** component tests mock `maplibre-gl`; the mock e2e suite serves a tiny PMTiles file of our own synthetic shapes (no map data) from the test server.
- **No geocoding** (our call): coordinates are typed or pasted in the wizard; nothing about a project is sent to a map service.
